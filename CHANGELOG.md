# Changelog

All notable changes to hyperui. Format: Keep a Changelog; versions follow SemVer.

## 0.13.1 — 2026-10-14
- **Design before spec when the change touches UI.** Screens, onboarding, components, layout or visual copy route to `design` first — even when the request says "SDD", "spec", "haz la spec" — for 2–3 directions; `spec` starts from the pick (its design phase cites `design.md`, never invents the UI); non-UI changes (backend, scripts, data) still go straight to `spec`.
- **Argued directions.** Every direction is critiqued internally against the brief's goal and presented with one "why it works" line naming the author/principle it leans on (Norman, Nielsen #n, ISO 9241-110, Shneiderman, Clark & Brennan, Munzner, Fogg/LIFT — sources from `skills/critique/references/`); the direction with the lowest critique severity is recommended with one sentence of why; `design.md` records both.
- **Dispatch threshold 3 → 2.** A `03-tasks.md` wave with ≥ 2 independent tasks (or ≥ 2 asked at once) launches one `hyperui:builder` per task in parallel (worktree isolation when files overlap) + `hyperui:reviewer` per task; the tasks gate recommends "Approve and build wave 1 in parallel (N tasks)"; UI tasks still get their browser check in the session and parallel builders still do not bump the version.
- **`npx @tizonai/hyperui update`** = `claude plugin marketplace update tizonai` then `claude plugin update hyperui@tizonai` (`--dry-run` supported; not installed yet → install). In the help text, the README and the session update hint.
- **npm trusted publishing** (`.github/workflows/publish.yml`): a `hyperui--v<version>` tag publishes to npm with `npm publish --provenance` via OIDC — no token; the job fails when the tag does not match `package.json`. README "Releasing" documents the one-time trusted-publisher setup.
- **Spec page converter wired.** `scripts/spec-page.py` (standard library only) turns a spec or critique markdown into the page: fragment for the Artifact tool (it wraps the skeleton), `--full` for the no-Artifact fallback; template resolved from the plugin tree, Mermaid pinned to 11.4.1, links/blockquotes/hr/HTML comments handled, `--self-test` (30 assertions) runs in `scripts/check.sh`; pre-approved by `permit.sh` and the `allowed-tools` of `spec`, `critique` and the root skill; hand-conversion only without `python3`.
- **Token economy rule** (root §5): concrete answers, detail on demand, specs/tasks written to execute without ambiguity (`OPEN:` for unknowns); propagated to the spec writing rules and task fields, the spec templates, the builder brief/report, design directions and critique findings.

## 0.13.0 — 2026-10-14
- **New specialist `diagram`: architecture, flow, sequence, data-flow and lifecycle diagrams that people explore and agents read.** The source of truth is a typed JSON IR (`skills/diagram/schema.json`: `schema_version`, `diagram_type`, `meta{title, lang, description, related, tokens}`, `layout` grid, `nodes[]` with `row`/`col` and the component types `frontend | backend | database | cloud | security | messagebus | external | actor`, `groups[]` (`boundary | lane | stage`), `edges[]` with variants `default | emphasis | security | dashed | return`, sides and `via`; `participants[]`/`messages[]` for sequences; `states[]`/`transitions[]` for lifecycles; unknown properties rejected at every level). The agent places by the authoring rules (`references/authoring.md`: main path first, stores and branches beside their owner, returns through the free corridor, 8–12 nodes per view, labels ≤ 24 chars, one emphasis per view; measured limits `0.6·font·units + 8`, `6.5·units + 21`, 8 px between boxes, 2 px edge clearance); `scripts/diagram-check.mjs` (Node ≥ 20, zero dependencies, deterministic) validates in repair order — `schema/*` → `layout/cell-collision` · `out-of-grid` → `layout/node-overlap` → `layout/text-fit` → `clean-flow/edge-through-node` → `clean-flow/endpoint-side-direction` → `composition/proper-crossing` (warning) → `composition/label-overlap` · `label-gap` → `layout/out-of-canvas` → `readability/projected-text` → `budget/too-many-nodes` (warning) — and every finding is `{code, severity, message, subject{collection,index,id,from,to}, evidence{px,points,bounds}, supportedFixes[]}` (`--json` one per line; catalogue in `references/diagnostics.md`). Ports start at side midpoints and spread at 14 px inside a 16 px gutter (aligned edges keep the midpoint); routes go straight → L → Z/U (mid-line pulled towards the source so fan-outs never cross) → shortest orthogonal path on a sparse grid; labels sit on the longest segment and slide to avoid nodes and group titles. The skill repairs at most twice, touching only the named subject, then delivers with the gap declared — never a silently broken drawing.
- **Self-contained viewer** (`templates/diagram/viewer.html`, rendered file < 60 KB, no fonts, no libraries): inline SVG with `<title>/<desc>`, colours only through CSS tokens (hyperui graphite + emerald, three-block light/dark theme, `meta.tokens.accent/font` from the project's `design.md`), opaque node masks and crossing halos, `data-node-*`/`data-edge-*` facts, nodes with `tabindex="0" role="button" aria-label`, click/keyboard focus with neighbours, upstream/downstream reach by BFS over the authored edges only, a passport panel (type, sublabel, incoming/outgoing), deep links `#focus=<id>&reach=up|down`, `?theme=light|dark`, PNG 2× and SVG export with the current tokens inlined, automatic legend of the types and variants present, chrome strings in `meta.lang` (en/es). The IR is embedded in `<script type="application/json" id="diagram-ir">`, identical to the `.json`.
- **Mermaid export and fast path**: `mermaid <ir.json>` writes `flowchart LR` (subgraph per group), `sequenceDiagram` or `stateDiagram-v2`; the skill answers inline Mermaid for READMEs, PR bodies, chat and systems with ≤ 6 nodes; `from-mermaid <file.mmd>` re-authors pasted Mermaid into an IR skeleton (ids, labels, edges, first `row`/`col` by rank) that the agent completes — the user's Mermaid is never edited.
- Files live in the **user's repo**: `<root>/.hyperui/diagrams/<name>.{json,html,mmd}`, published as an artifact (same url on every iteration; "add the queue between API and worker" edits the existing IR and keeps every other node's `row`/`col`), listed under `## Diagrams` in `design.md` (`templates/hyperui/design.md`) and in `state.md` `artifacts:`. Root `SKILL.md` routes "diagrama / arquitectura / flujo / secuencia / ciclo de vida / cómo se conecta" to `diagram`, adds the delivery gate (`0 errors` or a declared gap) and the care word `diagram validated`; `spec`'s design phase produces the architecture view and the happy-path sequence with `diagram` for backend + UI, multi-service and new-platform shapes (`design-template.md` row + "Authored diagrams"); `critique` and `patterns` read `.hyperui/diagrams/*.json` instead of a drawing; `permit.sh` pre-approves `node <root>/scripts/diagram-check.mjs …` (no chaining).
- Gate: `scripts/check.sh` runs `node --check scripts/*.mjs`, the toolchain's `--self-test` (38 cases written before the implementation: schema, layout, router, checks, render, Mermaid, output; fixtures inline + `references/examples/{architecture,flow,sequence,dataflow,lifecycle}.json`, all `0 errors`), a viewer-size lint (< 61440 bytes on every example render and every committed `.hyperui/diagrams/*.html`) and the Archify attribution lint. Attribution: `NOTICE` names Archify (MIT, commit `bb990b1`), `skills/diagram/LICENSE-archify` holds the full licence, every adapted helper carries `// Adapted from archify <path>@bb990b1 (MIT)`.
- Dogfooding: hyperui's own architecture is `.hyperui/diagrams/hyperui-architecture.{json,html,mmd}` (12 nodes, 13 edges; 2 findings on the first pass, 0 after one repair), screenshot in the README "Diagrams" section and the Mermaid embedded in `docs/architecture.md`. `docs/research/archify-diagram-method.md` (2026-10-08) is the method snapshot.

## 0.11.0 — 2026-10-06
- **New specialist `critique`: diagnose any UI against established HCI/UX theory and the product's goal.** Input: a live URL (captured at 360/768/1280 light + dark plus one interaction per `browser-verify.md`; headless Chrome fallback; with no browser tool the HTML is fetched and every visual check is reported as "to verify" — never a state that was not seen), screenshots or a designer's mock (read with the Read tool), Figma (through an MCP when one is listed, else an export), or a `.hyperui/` direction about to be built. The goal (sign-up · buy · download · read · contact · trust) is read from `brief.md`/`purpose` or asked in ONE question. Procedure = the evaluation procedure of the new research doc: the **22 merged checks** (Norman's principles, Nielsen's 10 heuristics, ISO 9241-110:2020, Shneiderman's 8 golden rules — `references/checklist.md`), the **conversation/repair walk-through** (gulf of execution → action → gulf of evaluation; grounding → breakdown → self-repair with input preserved → undo → closure — `references/repair-model.md`), a cognitive-load pass (one primary action per view, ≤ 4 chunks across steps, Gestalt grouping, squint-test hierarchy, scan path, Fitts), a Munzner pass for data views (delegating to the `viz` rules), an accessibility quick pass (contrast, focus, ≥ 44 px targets, labels), the platform-convention check (button order per platform, destructive styling, Cancel always present) and a **conversion lens by goal** (Fogg B=MAP at the CTA, LIFT, Baymard form rules, Core Web Vitals when measurable, dark patterns always severity 4 — `references/conversion-lens.md`). Every finding carries principle · evidence (viewport, element, screenshot) · severity 0–4 (Nielsen's scale) · concrete fix · effect on the goal; **top 3 by impact on the goal first**, then 2–4 specific "done well" items so the critique is fair (`references/severity-and-report.md`). Deliverable: `.hyperui/critique/<date>-<target>.md` + the same page as an artifact (`Critique — <target>`, through the spec page template; `.html` fallback), a reply with the top 3, strengths, the verdict line ("will this achieve <goal>? likely / at risk / no, because…"), the care line (`heuristics checked`) and the choice (fix the top 3 now (Recommended) · fix everything · explain a finding · stop; for someone else's site: design a direction that fixes the top 3 · spec the fixes). Sources only from `references/sources.md` (free first) — never an invented URL; the misreadings list (7±2 per screen, 3-click rule, Fitts as "make it big", F-pattern as a goal, "always confirm") is never propagated.
- **Critique before build.** Root §7 gate: UI directions and "done" UIs pass the critique checklist (severities 3–4 fixed before showing), then Impeccable. `design` runs the quick pass (cognitive load, match/consistency, feedback states, recovery paths, platform conventions) on each direction before presenting it and on each page in the QA step; the care line gains `heuristics checked`. Root §4 routes "revisa / critica / audita / evalúa este diseño", "¿está bien esta página?", "qué opinas de", a mock or a competitor's site to `critique`; a designer's mock before building → `critique` then `spec`.
- `docs/research/hci-ux-foundations.md` (research snapshot, 2026-10-06): concept map from the author's own design memories to the canonical names (Miller/Cowan, Hick–Hyman, Sweller, Gestalt, Fitts, Norman's affordances/signifiers/mapping/feedback/constraints, slips vs mistakes, mode errors, ISO 9241-110, the two gulfs, Clark & Brennan grounding, Schegloff repair, Grice, Laurel, Reeves & Nass), the 22 merged checks, the repair model, the conversion lens, the evaluation procedure with the 0–4 rubric and report template, a reading list (free first) and where popular summaries get it wrong. README "What the critique is grounded in", `docs/architecture.md` (tree, gates, `.hyperui/critique/`).

## 0.10.0 — 2026-10-04
- **hyperui keeps the user project's version honest.** From real use: hyperui changed a site and left it at 0.3.1 with no changelog line, so nobody could tell whether the deployed build had the change. New `skills/git/references/versioning.md`: SemVer policy per change — any code change → PATCH, a user-facing feature → MINOR, breaking → MAJOR only when the user confirms (MINOR while `0.y.z`); classification from the task/spec type or the Conventional Commit type (`feat` → minor; `fix|perf|refactor|style|chore` on code → patch; docs/tests/CI only → no bump); version source per stack (Node `package.json` + lockfile via `npm version --no-git-tag-version`, pnpm/yarn, Python `pyproject.toml`, Rust `Cargo.toml`, Dart `pubspec.yaml` `x.y.z+build`, Swift `CFBundleShortVersionString` + `CFBundleVersion` / `agvtool`, Java Gradle/Maven, Android `versionName`/`versionCode`, Go tag only); monorepo rule; Keep a Changelog block under the new version with today's date, user-facing bullets in the product's language, `CHANGELOG.md` created when missing; tag `vX.Y.Z` or the project's convention. `git` §3 commit flow is now classify → bump → changelog → stage both with the change → message with `Bumps to vX.Y.Z.` in the body (`chore(release): vX.Y.Z` for a pure release commit) → show and stop with a choice prompt → tag after merge/push; a new hard rule "never skip the bump"; `versioning: off` in `profile.md` (said in words: "no versioning for this project") honoured and silent; first bump recorded once in `decisions.md`. `build` §6/§7 and `hyperui:builder`: the bump + changelog line are part of "done" when code changed (builders running in parallel report `pending (parallel)` and the session bumps once); the care line lists `version vX.Y.Z`. `templates/hyperui/profile.md`: `versioning: auto  # auto | off` and `version_file: ""` (detected once, stored).
- **Visible and machine-readable version stamp in every UI project.** New `skills/design/references/version-stamp.md`: build-time injection of the version + short commit (host env: Amplify `AWS_COMMIT_ID`, Vercel `VERCEL_GIT_COMMIT_SHA`, Netlify `COMMIT_REF`, Cloudflare `CF_PAGES_COMMIT_SHA`, GitHub Actions `GITHUB_SHA`) per framework (Next.js `env`, Vite `define` + a tiny plugin, Angular generated `environment`, SvelteKit/Astro endpoints, Flutter `package_info_plus`, SwiftUI `Bundle.main`, Electron `app.getVersion()`, Tauri `getVersion()`); shown in the footer (small, muted, `title="Build"`) or Settings/About as `v1.4.2 · ab12cd3`; `<meta name="app-version" content="1.4.2+ab12cd3">` in the head AND a static `/version.json` (`{"version","commit","builtAt"}`) generated at build; a render test that the stamp shows the manifest's version; public info only. `design` (components + QA steps) and `build` add it on the first UI change of a project that has none.
- **Self-verification after a deploy.** `ship` §7 "Verify the deploy": read the expected version from the version file, run the new `scripts/verify-deploy.sh <url> <expected> [--timeout <s>] [--interval <s>] [--once]` (bash + curl; `/version.json` → `<meta name="app-version">` → the `v<x.y.z>` footer text, HTML comments stripped so React's `v<!-- -->0.3.1` reads; polls every 30 s up to 10 min; prints what it found; exit 0/1/2), report `deployed vX.Y.Z ✓` or `still vA.B.C after 10 min → check the host's build log`, give the user the one-liner `curl -s https://<domain>/version.json`, and record the result under `## Deploys` in `.hyperui/ship.md` (template updated); the care line says `deploy verified` only after an ✓. `deploy-recipes.md` §8 is the verify step; the script is pre-approved in the root and `ship` `allowed-tools` and in `permit.sh`.
- Root `SKILL.md` §7 gate: every code change ships with a bump + changelog entry, UI projects carry the stamp, deploys are verified before "live"; §9 care vocabulary gains `version vX.Y.Z` and `deploy verified`; §10 notes that parallel builders never bump. New eval `evals/version-bump` (Vite + React fixture at 0.3.1 with a stamp and an old changelog entry, dev/es, "cambia el texto del botón principal a 'Empezar' y deja listo el commit": `package.json` at 0.3.2, a `## [0.3.2] - 2026-…` changelog block, a proposed commit message naming 0.3.2, no `git commit` executed, Spanish, ends with options) — written, not yet run.
